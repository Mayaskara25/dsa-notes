1.1

Priority Queues & Why Heaps

The problem a heap exists to solve.

In a priority queue, elements are inserted with arbitrary priority, but removal always takes the element with the highest (max-priority queue) or lowest (min-priority queue) priority — never simply the oldest, as in an ordinary queue. A data structure supporting exactly these two operations (insert-with-priority, remove-the-best) is called a max (or min) priority queue.

A priority queue can be implemented with a plain unordered linked list: insertion is O(1) (just add anywhere), but removal requires scanning the entire list to find the largest-priority element first, which is O(n). A heap-based priority queue does both operations in O(log n) — the entire reason heaps exist as a data structure.

ImplementationInsertRemove-best
Unordered linked listO(1)O(n) — linear scan for the best element
HeapO(log n)O(log n)

A sorted linked list gives the opposite trade-off (O(n) insert, O(1) remove-best) — neither extreme is as balanced as a heap, which is why heaps are the standard priority-queue implementation. This connects directly to §1.9, where the heap operations built up in Part 2 are shown to be the priority queue's insert and remove-best.

1.2

Min-Heap / Max-Heap: Definition & Properties

One ordering rule, applied recursively, is the entire definition of a heap.

A heap is a complete binary tree that additionally satisfies the heap-order property:

  • Min-Heap: the key at every node is smaller than or equal to the keys of its children. This rule holds recursively for every subtree, so the smallest key in the whole tree is always at the root.
  • Max-Heap: the key at every node is greater than or equal to the keys of its children, recursively. The largest key is always at the root.
Fig 1. Max-Heap (left) and Min-Heap (right) — the heap-order property applied at every node.
"List the properties of a binary heap" — the full checklist
  • Shape property: a heap is always a complete binary tree — every level full except possibly the last, filled left to right (no gaps).
  • Heap-order property: every parent is ≥ its children (max-heap) or ≤ its children (min-heap), recursively.
  • Root extremum: the root always holds the maximum (max-heap) or minimum (min-heap) key — found in O(1).
  • No ordering between siblings or across subtrees — unlike a BST, a heap makes no left-vs-right comparison promise; only the parent-child relationship is constrained.
  • Array-storable: the shape property means a heap needs no pointers at all — see §1.3.
  • O(log n) insert and delete, because the tree's height is always O(log n) (guaranteed by the shape property).

1.3

Array Representation of a Heap

Because a heap is always a complete binary tree, its shape is entirely predictable — so parent/child links can be pure arithmetic instead of pointers.

Store the heap's elements in level order (root first, then each level left to right) into a plain array. For a node stored at 1-indexed position i:

parent(i) = i / 2 // integer division left_child(i) = 2*i right_child(i) = 2*i + 1

(0-indexed arrays shift these to parent(i)=(i-1)/2, left(i)=2i+1, right(i)=2i+2 — both conventions appear in textbooks; this guide uses 1-indexed for the diagram below and 0-indexed in the C-style code later, matching each source's own convention.)

1.4

Insertion (Sift-Up)

Add at the only position that keeps the shape complete, then restore the ordering by walking up.

  • Insert the new node as the last leaf, filling the array/tree left to right (this is the only position that keeps it a complete binary tree).
  • Compare the new node's value with its parent.
  • If the new node violates the heap order (greater than its parent in a max-heap; smaller in a min-heap), swap them.
  • Repeat steps 2-3 until the node satisfies the heap order relative to its parent, or it reaches the root.
    • Fig 3. Inserting 30 into the max-heap [20,15,12,4,3] (array [20,15,12,4,3,30] before sift-up): 30 starts as the left child of 12, swaps with 12, then with 20, and becomes the root; 12 ends in 30’s old slot. Result [30,15,20,4,3,12].
    // 0-indexed array; sift the newly-appended element up void siftUp(int a[], int i) { while (i > 0) { int parent = (i - 1) / 2; if (a[i] > a[parent]) { swap(a[i], a[parent]); i = parent; } else break; } } void insert(int a[], int *n, int value) { a[*n] = value; // place at the next free leaf siftUp(a, *n); (*n)++; }
    Worked example — Insert 95 into the max-heap [90,89,70,36,75,63,65,21,18,15].
    Fig 4. The tree after inserting 95: it started as the right child of 75, then swapped up past 75, 89 and 90 to the root (75 ends in 95’s old slot).
    Solution

    95 is placed at the next free leaf (position 11, the right child of 75's old parent). Compare with parent 75: 95>75, swap. New parent is 89: 95>89, swap. New parent is 90: 95>90, swap. Now at the root — stop. Final array: [95, 90, 70, 36, 89, 63, 65, 21, 18, 15, 75], i.e. the tree in Fig 4 — verified by simulating the sift-up in code.

    1.5

    Deletion (Sift-Down)

    A heap only ever supports deleting the root — the one element it guarantees is the best.

  • Swap the root with the last node in the heap.
  • Delete that last node (which now holds the old root's value) — this shrinks the heap by one while keeping it a complete tree.
  • Compare the new root with its left child.
  • If the root is smaller than its left child (max-heap), compare the left child with its right sibling; otherwise skip to step 6.
  • If the left child is larger than the right, swap root with the left child; otherwise swap root with the right child.
  • If the root is larger than its left child, compare the root with its right child instead.
  • If the root is smaller than the right child, swap with it; otherwise the process stops.
  • Repeat until the (moved) root value settles at its correct position.

    • In short: swap-to-last, remove, then repeatedly swap the out-of-place node with its larger child (max-heap) until it's ≥ both children or it has no children left — exactly the mirror image of sift-up, comparing down instead of up.

    // 0-indexed array; n = current heap size void siftDown(int a[], int i, int n) { while (1) { int l = 2*i+1, r = 2*i+2, largest = i; if (l < n && a[l] > a[largest]) largest = l; if (r < n && a[r] > a[largest]) largest = r; if (largest == i) break; swap(a[i], a[largest]); i = largest; } } int deleteMax(int a[], int *n) { int maxVal = a[0]; a[0] = a[--(*n)]; // move last node to root, shrink heap siftDown(a, 0, *n); return maxVal; }
    Worked example — delete the root (90) from an 11-node max-heap.
    Fig 5. Deleting the root (90) from an 11-node max-heap: 75 (the old last node) is promoted to root, then sifts down through 89 and 85 to settle in 85's old spot.
    Solution

    Array before: [90,89,70,36,85,63,65,21,18,15,75]. Swap root with last (75), remove the old root value (90): root is now 75, array shrinks to 10 elements. Sift down: 75's children are 89 and 70 — 89 is larger and >75, so swap; 75 moves to that position. Its new children are 36 and 85 — 85 is larger and >75, so swap again; 75 moves once more. Its new children are 15 and nothing (no right child) — 15 < 75, so it stops. Final array: [89,85,70,36,75,63,65,21,18,15] — verified by simulating swap-with-last plus sift-down in code, exact match to the source deck's own 10-step diagram trace.

    Building a Heap: Top-Down vs Bottom-Up Construction

    Two different ways to turn a plain list of values into a valid heap — one simple, one asymptotically faster.

    MethodIdeaCost
    Top-down (repeated insertion)Start with an empty heap; insert each value one at a time using the ordinary sift-up insertion from §1.4.O(n log n) overall
    Bottom-up (heapify)Drop all values into the array as-is (in input order); then sift-down every non-leaf node, starting from the last non-leaf and working back to the root.O(n) overall — asymptotically faster

    1.7

    Heap Sort

    Build a max-heap once, then repeatedly move its root to the end — an in-place, O(n log n) sort with no extra memory.

    Not in your materials — added for syllabus completeness Heap Sort does not appear in the source deck at all, but it is a syllabus-named application of Heap and is directly examined (RVCE SEE, Jan/Feb 2025, Part B Q7a). It needs no new machinery beyond build-heap (§1.6) and sift-down (§1.5), applied in a specific pattern.
  • Build a max-heap from the input array using bottom-up heapify (§1.6) — this takes O(n).
  • Swap the root (the current maximum) with the last element of the still-unsorted region.
  • Shrink the heap's boundary by one (the last position now holds a final, correctly-sorted value and is excluded from further heap operations).
  • Sift down the new root to restore the heap property within the shrunken heap.
  • Repeat steps 2-4 until only one element remains — the array is now sorted in ascending order.
    • // in-place, using the same siftDown from §1.5 void heapSort(int a[], int n) { for (int i = n/2 - 1; i >= 0; i--) siftDown(a, i, n); // build-max-heap, O(n) for (int end = n - 1; end > 0; end--) { swap(a[0], a[end]); // move current max to its final spot siftDown(a, 0, end); // restore heap on the shrunken region } }

    1.8

    Heap Sort Variations

    Descending order, partial sort for the k largest, and the named improvements.

    Not in your materials — added for syllabus completeness Only the plain ascending Heap Sort is in the notes above. Descending order, partial sort, and the named variants below are standard extensions added because the syllabus lists “Heap Sort variations”.

    The ascending Heap Sort of the previous section is one specific use of a heap’s defining ability — the best element is always at the root. Changing which element is “best”, or how many rounds are run, gives the useful variations below. All reuse the same two routines, siftDown and build-heap, so none needs new machinery.

    Variation 1 — sort in descending order (use a min-heap)

    Heap Sort drops the root at the end of the unsorted region on every round, so the end of the array receives whatever the root held. With a max-heap the back receives maxima, giving ascending order; with a min-heap the back receives minima, giving descending order. Only the comparison inside sift-down flips (< instead of >); the loop is unchanged. (The alternative — sort ascending, then reverse in O(n) — is equally correct; the min-heap version avoids the extra pass.)

    void buildMaxHeap(int a[], int n) { for (int i = n / 2 - 1; i >= 0; i--) siftDown(a, i, n); } /* Variation 1: descending order -> use a MIN-heap, same swap-to-the-end loop */ void heapSortDesc(int a[], int n) { for (int i = n / 2 - 1; i >= 0; i--) siftDownMin(a, i, n); // build-min-heap for (int end = n - 1; end > 0; end--) { swap(&a[0], &a[end]); // smallest goes to the back siftDownMin(a, 0, end); } } /* Variation 2: partial sort -> stop after k rounds; a[n-k..n-1] holds the k largest, ascending */ void partialHeapSort(int a[], int n, int k) { buildMaxHeap(a, n); // O(n) for (int end = n - 1; end > n - 1 - k && end > 0; end--) { // only k rounds, O(k log n) swap(&a[0], &a[end]); siftDown(a, 0, end); } }

    Top-K Elements Using a Heap

    Keep the k best items of a dataset or stream with a size-k heap instead of a full sort.

    Not in your materials — added for syllabus completeness Top-K elements is a syllabus-named heap application that appears in none of the source decks. Everything here is standard material; every trace was produced by running code.

    Problem. Given n items — possibly an endless stream — report the k largest (or the K-th largest) without sorting all n. Examples: the top 10 search results, the 5 highest scores so far, the 100 busiest URLs in a log.

    The counter-intuitive trick: use a MIN-heap of size k

    To keep the k largest seen so far, keep them in a min-heap. Its root is the smallest of the current top k — the one that would be evicted first. A new item x is therefore tested against the root only:

    1. Put the first k items into an array and run build-min-heap (O(k)).
    2. For every further item x: if x > root, overwrite the root with x and sift down (O(log k)); otherwise discard x in O(1).
    3. At the end the heap holds exactly the k largest items; its root is the k-th largest. Pop repeatedly (or sort the k items) if they must be reported in order.
    /* Top-K largest of a stream using a MIN-heap of size k: the root is the weakest of the current top k */ void siftDownMin(int a[], int i, int n) { for (;;) { int l = 2 * i + 1, r = 2 * i + 2, small = i; if (l < n && a[l] < a[small]) small = l; if (r < n && a[r] < a[small]) small = r; if (small == i) return; swap(&a[i], &a[small]); i = small; } } void topK(const int stream[], int n, int k, int heap[]) { for (int i = 0; i < k; i++) heap[i] = stream[i]; // first k items for (int i = k / 2 - 1; i >= 0; i--) siftDownMin(heap, i, k); // build-min-heap, O(k) for (int i = k; i < n; i++) if (stream[i] > heap[0]) { // beats the weakest of the top k heap[0] = stream[i]; // replace root, O(log k) siftDownMin(heap, 0, k); } }

    AVL Trees: Definition, Balance Factor & Rotations

    Named for Adelson-Velskii and Landis — a BST that rebalances itself so every operation stays O(log n).

    In an ordinary BST, the worst-case time for search/insert/delete is O(n) — a degenerate, skewed tree (the degenerate BST from the binary-tree notes) behaves like a linked list. An AVL tree is a BST that maintains an extra invariant after every insertion or deletion, guaranteeing the worst-case time for any operation stays O(log n).

    The AVL invariant
    balance factor(node) = height(left subtree) − height(right subtree)
    A tree is a valid AVL tree exactly when every node's balance factor is +1, 0, or −1. Any node whose balance factor becomes +2 or −2 after an insertion/deletion needs a rotation to restore the invariant.
    Balance factorMeaning
    0left and right subtrees have equal height
    +1left subtree is one level taller — still valid AVL
    −1right subtree is one level taller — still valid AVL
    +2 or −2invalid — a rotation is required

    Single rotations

    Fig 10. Single rotations: Left rotation fixes a straight right-right chain (bf −2); right rotation fixes a straight left-left chain (bf +2). Both verified: all resulting balance factors are 0.

    Double rotations

    A single rotation only fixes a straight chain (both imbalanced nodes leaning the same way). When the imbalance "zig-zags" — a node is left-heavy but its left child is right-heavy (or the mirror image) — a single rotation doesn't fix it and two rotations are needed instead.

    Fig 11. RL double rotation: a single left rotation alone wouldn't fix this (the right child 20 is itself left-heavy), so the right subtree is right-rotated first, turning it into a straight RR chain that a final left rotation resolves.

    The mirror-image case (LR: a left-heavy node whose left child is right-heavy) is fixed the same way in reverse: left-rotate the left child's subtree first, then right-rotate the node itself.

    CaseShapeFix
    LLleft-heavy, left child also left-heavysingle right rotation
    RRright-heavy, right child also right-heavysingle left rotation
    LRleft-heavy, left child right-heavyleft-rotate left child, then right-rotate node
    RLright-heavy, right child left-heavyright-rotate right child, then left-rotate node

    Why use an AVL tree for search?

    A plain BST fed already-sorted data (an ID column, timestamps, a sorted file being loaded) degenerates into a linked list, so search costs O(n). Inserting the seven keys 11–17 gives a BST of height 7; the AVL tree built from the same keys (Fig 12) has height 3, the minimum possible for 7 nodes. Because every node’s balance factor stays in {−1, 0, +1}, the height of an AVL tree with n nodes never exceeds about 1.44 log2(n+2), so search, insert and delete are all O(log n) in the worst case — the guarantee needed for in-memory dictionaries, symbol tables and ordered indexes (ordered iteration is free: an inorder walk). The price is one extra field per node (height or balance factor) and rotation work on updates.

    How skewed can an AVL tree be?

    Let N(h) be the fewest nodes an AVL tree of height h can have. The sparsest such tree has one subtree of height h−1 and one of height h−2, so N(h) = N(h−1) + N(h−2) + 1 with N(0)=0, N(1)=1 (a Fibonacci-like recurrence, which is where the 1.44 log n bound comes from).

    Height h123456
    Minimum nodes N(h)12471220

    So a tree of height 6 needs at least 20 nodes: an AVL tree cannot be tall and thin.

    B Tree: Definition, Properties & Insertion

    Multi-way balanced search trees: why nodes hold many keys, and how splits keep every leaf at the same depth.

    Not in your materials — added for syllabus completeness B Tree is named in the syllabus, but the supplied decks cover only the B+ tree. This section (definition, insertion with splits, deletion, lab program) is added; the B+ tree and the B vs B+ comparison follow.

    Why B-trees exist

    A BST or AVL tree has one key per node, so a tree of a million keys is about 20 levels deep — 20 pointer hops, and if the data lives on disk each hop is a separate slow disk read. A B-tree is a balanced multi-way search tree: one node holds many sorted keys (sized to fill a disk page), so each node read narrows the search by a factor of hundreds and the tree stays only a few levels deep. It is the foundation of database indexes and file systems.

    Definition (order m)

    A B-tree of order m is a search tree in which:

    1. every node has at most m children and therefore at most m − 1 keys;
    2. the root has at least 2 children if it is not a leaf (so at least 1 key);
    3. every other internal node has at least ⌈m/2⌉ children, i.e. at least ⌈m/2⌉ − 1 keys; every leaf (except a root leaf) has at least ⌈m/2⌉ − 1 keys;
    4. all leaves are on the same level — the tree is perfectly height-balanced;
    5. a node with j keys k1 < … < kj has j + 1 children; child i holds only keys between ki−1 and ki;
    6. a key and its record may sit in any node, internal or leaf, and each key appears exactly once.
    Convention warning This guide defines the order as the maximum number of children, the same convention used by the B+ tree section below and by the question-paper answers (max 7 pointers → order 7). Some textbooks (CLRS, for instance) instead use a minimum degree t, giving up to 2t children and 2t − 1 keys. If a question gives numbers, state which convention you are using; the shape of the answer does not change.

    Height

    With t = ⌈m/2⌉, a B-tree holding n keys has height h ≤ logt((n+1)/2) (height counted in edges). For order m = 101 (t = 51) and n = 1,000,000 keys this is log51(500000.5) = 3.34, so h ≤ 3: at most 4 node reads to find any key among a million. A balanced BST would need about 20.

    Search

    Start at the root; inside a node find the first key ≥ the target (linear or binary scan — the node is in memory once read). If it equals the target, stop; otherwise follow the child pointer to its left; at a leaf with no match the key is absent. Cost: one node read per level, so O(logt n) disk reads. Unlike a B+ tree, a B-tree search can finish early, at an internal node.

    Insertion with splits

    1. Search for the correct leaf and insert the key into it in sorted position.
    2. If the node now has m keys (one too many), split it around the median key: the keys left of the median stay, the keys right of it move to a new sibling node, and the median moves up into the parent (between the pointers to the two halves).
    3. The parent has gained a key, so it may overflow in turn: repeat step 2 upward.
    4. If the root splits, create a new root holding only the median — this is the only event that increases the tree’s height, and it keeps all leaves at the same depth.

    Splitting on overflow keeps every node at least half full: a node of m keys splits into two nodes of about (m−1)/2 keys each, which is exactly the minimum.

    Deletion — overview

    Deletion is the mirror image of insertion: where insertion fixes overflow by splitting, deletion fixes underflow (a non-root node falling below the minimum number of keys) by borrowing or merging.

    1. Key in an internal node: replace it by its inorder predecessor (largest key in the left subtree) or successor, then delete that key from its leaf instead. So every deletion ends in a leaf.
    2. Leaf still has at least the minimum after removal: done.
    3. Underflow, and an adjacent sibling has a spare key: borrow — rotate through the parent: the sibling’s nearest key moves up, the parent’s separator moves down into the underfull node.
    4. Underflow, and siblings are at the minimum: merge the node, its sibling and the separator pulled down from the parent into one node. The parent has lost a key, so repeat the check on the parent. If the root loses its last key, the merged child becomes the new root and the height decreases.

    B+ Trees

    The tree structure behind almost every database index and filesystem directory — a search tree tuned to minimize disk reads.

    A B+ tree is a balanced multi-way search tree where, unlike a BST, all actual data lives in the leaf nodes. Internal nodes hold only separator keys used to route a search to the correct leaf — they are a pure index structure, never storing data themselves. All leaves sit at the same depth (perfectly balanced), and leaves are linked left-to-right in a chain, making range queries ("give me everything between X and Y") a simple linked-list walk once the starting leaf is found.

    Appraisal — why B+ trees, as a tree-based data structure (QP1 Q3.a)
    • High fan-out: each internal node can have many children (order n), so the tree stays shallow even for millions of records — minimizing the number of (slow) disk reads needed per search, which is the entire reason B+ trees dominate in databases and filesystems over binary structures.
    • Uniform leaf depth: every search, successful or not, touches exactly the same number of levels — predictable worst-case performance, unlike a BST.
    • Linked leaves give efficient sequential/range access, something a plain BST or B-tree (which may store data in internal nodes too) doesn't offer as directly.
    • Trade-off: separator keys are sometimes duplicated between an internal node and a leaf, using slightly more space than a B-tree — an acceptable cost for the range-query and disk-I/O benefits above.
    Not in your materials — added for syllabus completeness Neither source covers B+ tree capacity formulas.     Application — B/B+ trees for database indexing

    A database stores rows in fixed-size disk pages. Reading one page costs milliseconds, orders of magnitude more than any in-memory work on it, so the quantity to minimise is page reads. An index is a B+ tree whose node size equals the page size: every node read is one page read, and the fan-out is as large as a page allows.

    Worked estimateillustrative
    How many page reads does an index lookup need among 109 rows, if a page is 8 KB and an index entry (key + pointer) is 12 bytes?
    Solution

    Entries per page: ⌊8192 / 12⌋ = 682, so order m ≈ 682. Levels needed at full fan-out: ⌈log682(109)⌉ = 4; even if every node is only half full (≈ 341 children), ⌈log341(109)⌉ = 4. A billion-row lookup is therefore about 4 page reads (the top levels are usually cached, so often 1–2 real disk reads), against about 30 for a balanced binary tree. (The sizes are assumptions chosen for the arithmetic; real systems vary.)

    • Equality lookup (WHERE id = 42): descend root → leaf, follow the row pointer.
    • Range / ORDER BY (WHERE id BETWEEN 100 AND 200): descend once to the leaf holding 100, then walk the linked leaves until 200 — the reason databases choose B+ trees over B-trees.
    • MySQL InnoDB tables and PostgreSQL’s default btree index are B+-tree variants.
    • Inserts that overflow a page split it (Fig 15–17), so the index stays balanced as the table grows.

    Splay Trees

    A self-organizing BST that keeps recently-touched elements near the root.

    A splay tree is a self-organizing BST with the property that whichever element was most recently inserted or accessed becomes the new root, via a sequence of rotations called splaying. Invented by Daniel Sleator and Robert Tarjan. No balance factor is maintained explicitly — the tree simply reshapes itself around usage patterns, which is why it excels whenever the same items tend to be accessed repeatedly in a short window.

    ApplicationWhy splay trees fit
    Cache memoryRecently-used entries end up near the root, so repeat lookups are fast
    Virtual memory managementSame locality-of-reference argument for recently-accessed pages
    Routing tablesFrequently-used routes surface near the root

    Why a splay tree behaves like a cache

    A cache keeps recently or frequently used items cheap to reach. A splay tree does this with no extra bookkeeping: every access — even a read-only search — splays the accessed node to the root. The next access to the same key therefore costs one comparison. Items used a moment ago stay near the top; items nobody touches drift down as other nodes are rotated above them. This gives the working-set behaviour of an LRU cache without a counter or timestamp. The guarantee is amortised: m operations on an n-node splay tree cost O(m log n) in total, even though one single access may touch O(n) nodes.

    • A conventional cache with a fixed size and an eviction policy (LRU) is usually a hash table plus a doubly linked list — see the hashing application section. The splay tree is the self-adjusting search-tree analogue.
    • Other uses: routing tables (popular prefixes surface), virtual-memory page tables, and text compression models.

    Tries

    A tree shaped by shared prefixes — the standard structure for representing a set of strings.

    A Trie (the name comes from retrieval) is a multi-way search tree used to implement a dictionary — the most popular data structure for representing a set of strings. Each edge is labelled with a character; a path from the root spells out a prefix, and certain nodes are marked as "end of word." Because words sharing a prefix share the same path from the root, a Trie's shape is determined entirely by the set of strings stored — not by the order they were inserted (unlike a BST, where insertion order changes the shape).

    TypeStructure
    Standard TrieOne node per character — simple, but wastes space on long unbranching chains.
    Compressed TrieCollapses every chain of single-child nodes into one edge labelled with the whole substring — saves space whenever a prefix isn't shared by anything else.

    Node design

    Each node holds an array of 26 child pointers (one per letter) and an isWord flag. The letter of an edge is implied by the array index, so a word is spelled by following indices from the root, and the flag says whether a stored word ends at that node (this is what separates me from the prefix of men).

    Operations

    OperationHowCost (word length L)
    insert(w)follow / create one node per letter; set isWord at the lastO(L)
    search(w)follow letters; succeed only if the path exists and isWord is setO(L)
    startsWith(p)follow letters of p; succeed if the path exists (no flag needed)O(|p|)
    autocomplete(p)walk to the node for p, then DFS its subtree in a–z order, printing every node with isWordO(|p| + size of the subtree)
    delete(w)un-mark isWord; free nodes on the way back that have no children and no word ending thereO(L)

    All costs depend on the word length, not on how many words are stored — a trie with a million words finds a 10-letter word in 10 steps. A hash table is also expected O(L) (it must hash the whole string) but cannot do prefix queries.

    Degree and the handshake lemma

    In an undirected graph every edge has two ends, so it adds exactly 2 to the total degree: Σ deg(v) = 2|E|. In a directed graph every edge leaves one vertex and enters another, so Σ in-degree = Σ out-degree = |E|. A consequence: the number of odd-degree vertices is always even.

    Graph Traversal: BFS & DFS

    Both algorithms in C, with queue/stack traces and visit orders computed on one example graph.

    Not in your materials — added for syllabus completeness BFS and DFS algorithms are named in the syllabus (“Pathfinding (BFS/DFS)”) but are not in any supplied source. Code and traces below are compiled and computed.

    A graph traversal visits every vertex reachable from a start vertex exactly once. Because a graph can contain cycles, every traversal needs a visited record; without it the walk would loop forever.

    • Breadth-First Search (BFS) explores in rings: all vertices 1 edge from the start, then 2 edges, and so on. It uses a queue.
    • Depth-First Search (DFS) goes as deep as possible along one path, then backtracks. It uses a stack (or the recursion stack).

    Representation used

    Adjacency lists, with each vertex’s neighbours stored in alphabetical order. G1 (Fig 26) is stored as:

    BFS

    1. Mark the start vertex discovered (distance 0) and enqueue it.
    2. While the queue is not empty: dequeue u and visit it; for each neighbour v not yet discovered, mark it, record dist[v] = dist[u] + 1 and parent[v] = u, and enqueue it.
    void bfs(int s, int dist[], int parent[]) { int queue[MAXV], head = 0, tail = 0; for (int i = 0; i < V; i++) dist[i] = -1, parent[i] = -1; // -1 = not yet discovered dist[s] = 0; queue[tail++] = s; while (head < tail) { int u = queue[head++]; // dequeue printf("%c ", 'A' + u); // "visit" u for (Edge *e = adj[u]; e; e = e->next) if (dist[e->to] < 0) { // first time we see this vertex dist[e->to] = dist[u] + 1; // one edge further than u parent[e->to] = u; queue[tail++] = e->to; // enqueue } } }

    Hash Tables: ADT Context & Applications

    Why hashing exists: making the Set/Map ADT's operations run in expected O(1) time.

    An Abstract Data Type (ADT) specifies what operations a structure supports and what properties they guarantee — never how they're implemented internally. A Set ADT, for instance, maintains a collection under three operations: insert(x), delete(x), and search(x) (does x belong to the set?), with the property that the set holds no duplicates. Hash tables are one of the most common ways to implement a Set (or Map) ADT.

    A hash table stores key/value pairs and uses a hash function to compute an array index for each key directly, rather than searching for it. Under reasonable assumptions about the hash function and the data, the average time to search, insert, or delete is O(1) — dramatically faster than a linear scan (O(n)) or even a balanced BST (O(log n)).

    Applications

    ApplicationHow hashing is used
    Message digests (cryptography)Alice hashes a message and sends both the message and its digest; Bob re-hashes the received message and compares digests — a mismatch means the message was altered in transit.
    Password verificationA password is salted and hashed before storage; at login, the entered password is salted and hashed the same way and compared — the plaintext password itself is never stored.
    Rabin-Karp algorithm (plagiarism/substring checking)Compares the hash of a pattern against the hash of each equal-length window of the text; only when hash values match does it fall back to a full character comparison, making bulk scanning fast.
    A note on the deeper theory (condensed) The source deck also develops a more formal, CLRS-style treatment: the integer-universe assumption (keys are drawn from U={0,…,u−1}, and a hash function maps them into {0,…,m−1}), the random-probing assumption (each key behaves as if it comes with an infinite random probe sequence), and universal hashing (choosing a hash function at random from a carefully designed family H guarantees a low expected collision rate for any input, defeating adversarial worst-case inputs). These formalize why hashing works well on average — useful background, but not the focus of the worked exam questions in this unit, so kept brief here rather than derived in full.

    Hash Functions: Division & Multiplication Methods

    Two standard ways to turn a key into a table index.

    Division method

    h(x) = x mod m

    The simplest and most common hash function — divide the key by the table size m and keep the remainder. Works best when m is chosen to avoid regularities in the key distribution (a prime m, not too close to a power of 2, is the usual recommendation).

    Multiplication method

    h(x) = ⌊m · (x·A mod 1)⌋ // A is a real constant, 0 < A < 1

    Multiply the key by a constant A, keep only the fractional part, then scale up by m and floor it. Its main advantage: the choice of m is not critical — m can be a convenient power of 2 (useful on binary computers), unlike the division method where m's properties (e.g. primality) matter. Knuth suggests using the reciprocal of the golden ratio, A ≈ 0.618, as it tends to spread keys particularly evenly regardless of patterns in the input.

    Why "the value of m is not critical" matters With the division method, a poorly chosen m (e.g. a power of 2 when keys share low-order bit patterns) can cause severe clustering. The multiplication method's behaviour depends on A, not m — so m can be picked purely for implementation convenience (a power of 2 lets the multiply-and-shift be done with fast bitwise operations) without hurting distribution quality.

    Open Hashing (Separate Chaining)

    Let each slot hold more than one element — collisions become a linked-list append, not a crisis.

    Open Hashing (also called separate chaining) resolves collisions by letting each table slot A[i] point to the head of a linked list of every key that hashes to i. Inserting x means appending it to the list at A[h(x)]; searching or deleting means walking that one list.

    struct Node { int key; struct Node* next; }; struct Node* table[M]; // M linked-list heads, one per slot void insert(int key) { int i = h(key); struct Node* n = malloc(sizeof(struct Node)); n->key = key; n->next = table[i]; table[i] = n; // insert at the head — O(1) } struct Node* search(int key) { struct Node* cur = table[h(key)]; while (cur && cur->key != key) cur = cur->next; return cur; // O(1 + length of this one list) }
    OperationCost
    InsertO(1), even worst case — always appends at the head
    Search / DeleteO(1 + α) expected, where α = n/m is the load factor (average chain length)
    Load factor α = n/m With n keys stored across m slots, each slot holds n/m keys on average if the hash function distributes keys uniformly. Keeping α around 1 (by resizing the table as n grows) is what keeps chaining's O(1+α) search bound close to O(1) in practice.

    Closed Hashing (Linear, Quadratic & Double Hashing)

    Every key lives directly in the table itself — collisions are resolved by probing for the next free slot.

    Closed Hashing (also called open addressing) allows each table slot to store only one value. When a collision occurs at slot i, one of the two competing keys must move on to the next slot in its probe sequence — a fixed rule for generating "where to try next" that all three techniques below share the same goal for, but generate differently.

    Linear probing

    index(x, i) = (h(x) + i) mod m, i = 0, 1, 2, …

    On collision, simply try the next slot, then the next, wrapping around the table if necessary. Simple, but prone to primary clustering — once a run of occupied slots forms, it keeps growing, since any key hashing anywhere inside the run has to probe through the whole thing.

    Probe distances grow quadratically (1, 4, 9, 16, …) instead of linearly, which spreads collisions out much faster and avoids primary clustering — though it introduces a milder secondary clustering (keys that collide at the same slot follow the exact same probe sequence).

    Double hashing

    index(x, i) = (h1(x) + i · h2(x)) mod m, i = 0, 1, 2, …

    Uses two independent hash functions: h1 picks the starting slot, and h2 determines the step size for probing on collision — since the step size itself now varies by key, even two keys that collide at the same starting slot will usually follow completely different probe sequences, avoiding secondary clustering altogether. This is generally the best-spreading of the three open-addressing techniques.

    Lab: Double Hashing Program

    Closed hashing with a key-dependent step: choosing h2, the C program and a verified trace.

    Not in your materials — added for syllabus completeness Double hashing has a worked example in your notes but no program. The lab program (and the guidance on choosing h2) is added.

    Recap and the rule for choosing h2

    index(k, i) = ( h1(k) + i × h2(k) ) mod m, i = 0, 1, 2, …

    h1 gives the home slot; h2 gives a key-specific step. Two requirements make the probe sequence visit every slot:

    1. h2(k) ≠ 0 for every key — a step of 0 never moves (this is the flaw noted for h2 = (x+5) mod 10 in the earlier section).
    2. gcd(h2(k), m) = 1. The easiest way: make m prime and keep 1 ≤ h2(k) < m. A common choice is h2(k) = R − (k mod R) with R a prime smaller than m, which yields a step in 1..R.

    Why the second rule matters, computed: with m = 10 and a step of 5 starting at slot 3 the probes are 3, 8, 3, 8, 3, 8… — only the two slots {3, 8} are ever tried, although the table may have eight empty slots. With m = 11 (prime) and a step of 3 the probes 3, 6, 9, 1, 4, 7, 10, 2, 5, 8, 0 visit all 11 slots exactly once.

    Lab program — double hashing in C

    m = 11 (prime), h1(k) = k mod 11, h2(k) = 7 − (k mod 7). Insert and search follow the same probe sequence; search stops at the first empty slot.

    RVCE CIE-III · 07 Jan 2025 · Part B Q5.b6 marks
    Mention the properties of hash function. Given two hash functions, h1 and h2 defined by h1(x)=(3x+11) mod 17 and h2(x)=5x mod 29, identify which is better w.r.t collision resistance. Being a cyber-forensic expert, the original hard drive and image are handed to you. How do you take a decision and generate the report?
    Properties of a good hash function

    Deterministic (same key always gives the same index); fast to compute; distributes keys uniformly across the table (minimizes collisions); small changes in the key should ideally produce large, unpredictable changes in the output (avalanche effect, especially important for cryptographic uses).

    Comparing h1 and h2

    h1 maps into a table of size 17, h2 into a table of size 29 — a larger table (h2) spreads the same number of keys more thinly, giving fewer expected collisions purely from the pigeonhole effect. Both are linear congruential forms; 17 and 29 are both prime, which is good practice for the division method (§4.2) since it avoids common-factor clustering with structured input. All else equal, h2 is the better choice for collision resistance, simply because its table is larger relative to any fixed key set — the same reasoning as load factor α=n/m in §4.3: a bigger m directly lowers α.

    The forensic-imaging scenario

    This ties directly to the Message Digest application from §4.1: to verify a disk image is a faithful, unaltered copy of the original hard drive, a forensic expert computes a cryptographic hash (e.g. SHA-256) of the original drive and of the image, then compares the two digests. Identical hashes are strong evidence the image is bit-for-bit identical to the original (the same "compute → compare" pattern as Fig-style message-digest verification); any mismatch means the image cannot be trusted as evidence, and the report must document exactly which hash algorithm was used, both digest values, and the match/mismatch result as the basis for the finding.

    Hashing Applications: Symbol Tables, Caching & Indexing

    Three syllabus-listed uses of hash tables, each with a computed example.

    1. Symbol table in a compiler

    A compiler must answer, millions of times per program, “has this identifier been declared, and what is its type, scope and address?” The symbol table is a hash table keyed by identifier name: a declaration inserts, every later use looks up, and a second declaration of the same name in the same scope is found by the lookup and reported as an error. Expected O(1) per operation keeps compilation linear in program size. Nested scopes are handled by a stack of tables (or one table whose chains hold a scope level): on leaving a block the innermost table is discarded.

    2. Caching

    A cache stores recent results so repeated requests avoid the slow path (disk, network, recomputation). The lookup “is this key in the cache?” must be O(1) — a hash table. Browsers (URL → page), DNS resolvers (name → address), and memoised functions (arguments → result) all work this way. A fixed-size cache also needs an eviction rule; the standard LRU cache evicts the least recently used entry and combines a hash table (key → list node, for O(1) lookup) with a doubly linked list ordered by recency (for O(1) move-to-front and evict-from-back), so both get and put are O(1).

    3. Database indexing

    A hash index maps a column value to the rows that hold it through a hash function, giving expected O(1) equality lookups (WHERE email = ...).
